## **1. Introduction**

This report documents the development lifecycle of `lsh`, a custom UNIX shell implemented as part of a laboratory assignment. The goal was to construct a functional command-line interpreter that serves as a middleware between the user and the operating system, capable of parsing user input, creating processes, and managing inter-process communication. The project had a skeleton parser which handled the complex task of lexical analysis and syntactic parsing, returning a structured `Command` object. Our primary responsibility was to build the execution engine from the ground up, utilizing fundamental UNIX system calls such as `fork()`, `execvp()`, `waitpid()`, `pipe()`, and `dup2()`, while strictly adhering to the constraint of not delegating command execution to any existing shell via `system()` or similar mechanisms. This report will explore how the lab specifications were met, the order of implementation, challenges encountered, and provide feedback on the laboratory materials and testing procedures.

## **2. Order of fulfillment of Specifications**

We successfully implemented all specifications for the `lsh` shell. The following is a detailed account of how each requirement was met and validated.

**1. Ctrl-D Handling:** The shell gracefully exits upon receiving an End-of-File (EOF) signal, which is typically generated by the user pressing Ctrl-D. This was achieved by checking the return value of the `readline()` library function; a `NULL` return value indicates EOF, which triggers a clean exit from the main command loop.

**2. Basic Commands with PATH:** The shell correctly executes simple commands like `ls` and `date`. This functionality is driven by the `execvp()` system call, which automatically searches for the executable in the directories listed in the `PATH` environment variable. If a command is not found, `execvp()` fails, and an appropriate error message is printed to the user.

**3. Built-in Commands:** The `cd` and `exit` commands are implemented as built-ins, meaning they are executed directly within the shell process itself without forking a child. The `cd` command uses the `chdir()` system call, and the `exit` command breaks the main loop, leading to a graceful termination.

**4. Piping:** The shell supports the creation of pipelines with one or more commands (e.g., `ls | grep .c | wc -l`).

**5. Background Execution:** Commands terminated with an ampersand (`&`) are executed in the background. The shell identifies the `background` flag in the parsed `Command` structure and, after forking the child process, does not call `waitpid()` immediately. This allows the parent shell process to return to the prompt without delay, while the child process runs concurrently.

**6. I/O Redirection:** The shell handles two forms of redirection: input (`<`), output (`>`). The logic correctly applies input redirection only to the first command in a pipeline and output redirection only to the last command. This is implemented using `open()` and `dup2()` to reassign standard input (`STDIN_FILENO`) or standard output (`STDOUT_FILENO`) to the specified files before calling `execvp()`.
